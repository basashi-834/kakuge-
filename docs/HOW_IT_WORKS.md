# しくみの解説（どこが、どうなって、こうなるのか）

このゲームが「ボタンを押してから、相手の体力が減るまで」に何をしているのかを、
**順番どおりに** 追いかける文書です。プログラムを読む前にここを読むと、
「どのファイルを開けばいいのか」が分かるようになります。

各ファイルの先頭にも同じ調子の説明が書いてあります。この文書は
**ファイルとファイルのつなぎ目**、つまり「1 つのファイルを読んでも
分からないこと」を担当します。

---

## 0. いちばん大事な考え方: 2 つの世界に分けてある

```
src/engine/    … 戦闘のルール（SDL2 も Windows も一切使わない）
src/platform/  … 画面・音・入力（SDL2 を使う）
```

`engine/` は「画面に何も出さなくても動く」ように作ってあります。
だから `tests/EngineTests.cpp` は、ウィンドウを 1 つも開かずに
「弱パンチをガードしたら本当に -1 フレーム不利になるか」を
1 フレーム単位で検証できます。

この分け方には、初心者にとって大きな利点があります。
**バグが出たとき、探す場所が半分になります。**

| こういう症状 | 見るのは |
|---|---|
| 技のフレームが合わない、当たらない、コンボがつながらない | `engine/` |
| 絵がずれる、色がおかしい、キーが効かない、画面が出ない | `platform/` |

## 1. 1 フレーム（1/60 秒）に何が起きているか

ゲームは 1 秒間に 60 回、まったく同じ順番で次を繰り返しています。
順番が固定されているので、**同じ入力からは必ず同じ結果が出ます**
（再現性がある＝バグを追いかけられる）。

```
Game::Run()                         … platform/Game.cpp
  │
  ├─ HandleEvents()                 キーボード・マウス・パッドの生の入力を集める
  │
  ├─ Update(dt)
  │   └─ 固定タイムステップのループ（1/60 秒ぶんずつ進める）
  │        └─ BattleSystem::Update(1/60, 1P の入力)   … engine/BattleSystem.h
  │             │
  │             ├─ ① CPUAI::Decide()        2P の入力を「考えて」作る
  │             │      ※ 人間と同じ RawInput しか作れません
  │             │
  │             ├─ ② Player1.FrameStep()    1P を 1 フレーム進める
  │             ├─ ③ Player2.FrameStep()    2P を 1 フレーム進める
  │             │      ※ 順番は必ず 1P → 2P（固定）
  │             │
  │             ├─ ④ ResolvePushboxes()     体が重なっていたら押し離す
  │             ├─ ⑤ ResolveMaxDistance()   離れすぎないように寄せる
  │             │
  │             ├─ ⑥ ResolveCombat(1P→2P)   1P の攻撃が 2P に当たったか
  │             ├─ ⑦ ResolveCombat(2P→1P)   2P の攻撃が 1P に当たったか
  │             │
  │             ├─ ⑧ UpdateProjectiles()    飛び道具を進める・当てる
  │             └─ ⑨ 制限時間・KO の判定
  │
  └─ Render()                       今の状態を絵にする（状態は変えない）
```

### なぜ「攻撃の判定」が ②③ ではなく ⑥⑦ なのか

もし Fighter が自分で「相手に当たったか」を調べると、1P と 2P が
それぞれ勝手に判定してしまい、**どちらが先に当たったかが状況で変わります**。
相打ちのはずが片方だけ勝つ、といったことが起きます。

そこで審判役（`BattleSystem`）が 1 人だけ判定します。
2 人を先に動かしきってから、同じ 1 つの盤面に対して判定するので、
相打ちは必ず相打ちになります。

### 「時間が止まる」とはどういうことか

攻撃が当たった瞬間、両者が数フレーム完全に止まります（ヒットストップ）。
これが「殴った手応え」の正体です。

止まっている間、`Fighter::FrameStep` は
**入力の記録だけして、すぐ帰ります**（`HitstopTimer > 0` のとき）。
座標もアニメも硬直タイマーも動きません。
入力だけ受け付けるのは、止まっている間に押したボタンを
「先行入力」として覚えておくためです（→ 5 章）。

## 2. 当たり判定は 3 種類ある（混ぜてはいけない）

格闘ゲームの当たり判定は、絵の形とはまったく関係ありません。
目に見えない四角形どうしが重なったかどうかだけで決まります。

| 名前 | 何を表すか | 色（`F1` の表示・エディタ共通） | 持っている場所 |
|---|---|---|---|
| ヒットボックス | 攻撃が当たる範囲 | 赤 | 技のデータ（`MoveData::Hitboxes`） |
| ハートボックス | 自分の食らう範囲＝体 | 緑 | キャラクター（姿勢ごと）＋技ごと |
| プッシュボックス | 体と体が押し合う範囲 | 青 | キャラクター（姿勢ごと） |

**判定のルールはたった 1 つです。**

> 攻撃側の「ヒットボックス」と、防御側の「ハートボックス」が重なったらヒット。

ヒットボックスどうしは絶対に判定しません（だから技と技はすり抜けます）。
プッシュボックスは攻撃に一切関係しません（押し合いだけの担当です）。

### 食らい判定は 3 段構えで決まる

`Fighter::HurtboxRects()`（`engine/Fighter.h`）が、上から順に調べます。

```
1. 技の frameBoxes の hurtboxes … 「4〜6F 目だけ」のような、フレーム単位の指定
2. 技の hurtboxes               … その技を出している間ずっと
3. 姿勢ごとの標準               … 立ち / しゃがみ / 空中（技を出していないとき）
```

2 が「技ごとの食らい判定」です。足払いで前へ脚を伸ばすと、
**伸ばした脚がそのまま殴られる場所になります。**
これがないと「攻撃判定だけ伸びて、体は突っ立ったまま」になり、
伸びた脚を狙って潰す、という差し合いが成立しません。

技が終われば（状態が `Attack` でなくなれば）、自動的に 3 に戻ります。

## 3. 技が始まってから終わるまで

### フレームの数え方（このゲーム全体で統一）

フレームは **1 から** 数えます。技を出したフレームが 1F 目です。
「発生 4F」は「**4F 目に**最初の攻撃判定が出る」という意味で、
「4F 待ってから 5F 目に出る」ではありません。

```
発生 4F / 持続 3F / 硬直 7F の技

  1F  2F  3F | 4F  5F  6F | 7F ...... 13F | 14F
  ← 発生前 →   ← 攻撃判定 →  ←  硬 直  →   行動可能

全体フレーム = (発生 - 1) + 持続 + 硬直 = 3 + 3 + 7 = 13F
```

「今が何段階目か」を答えるのは `MoveExecutor::GetPhase()` です。
この関数は**状態を一切持ちません**。経過フレーム数から毎回計算し直すので、
「実際のフレーム数と進行状況がずれる」バグが原理的に起きません。

### 技を出す（`Fighter::TryStartMove`）

出せる技を探す順番が決まっています。

```
超必殺技 → 必殺技 → 通常技
```

逆にすると、波動拳コマンドを入れても先に立ち弱パンチが出てしまい、
必殺技が永久に出せなくなります。

姿勢（立ち技かしゃがみ技か）は「**今フレームのレバー**」で決めます。
状態（立ち / しゃがみ）で決めてはいけません。下＋ボタンを同時に押した
最初のフレームは、状態がまだ「立ち」だからです（しゃがみに変わるのは
このあとの処理）。それだと、しゃがみたいのに立ち技が出ます。

### 硬直差とのけぞり時間

このゲームでは、**データに書くのは「硬直差」だけ**です。
のけぞり時間（相手が動けない長さ）は、そこから逆算されます。

```
のけぞり ＝ 硬直差 ＋ (持続 ＋ 硬直)
```

なぜこうするのか。もし「硬直差」と「のけぞり時間」を別々に手入力できると、
必ずどこかで食い違い、**表に書いた数字と実際の挙動が違う**という、
格闘ゲームでいちばんたちの悪いバグになります。
片方だけを入力にして、もう片方は必ず計算で出す、と決めておけば
永久に食い違いません。

## 4. データ（JSON）が画面に届くまで

```
data/characters/ryu.json   キャラクターの性能（体力・速度・姿勢ごとの判定）
data/moves/ryu/*.json      技 1 つにつき 1 ファイル
        │
        ↓  起動時に読む
 DataManager::ReloadAll()                    … engine/DataManager.h
        │   BaseDir（data/）→ UserDir（%APPDATA%\Kakuge\）の順に読む
        │   ＝ 同じ ID があればユーザーの編集が勝つ
        ↓
 CharacterStats / MoveData（プログラム上の形）  … engine/*.h の FromJson()
        ↓
 Fighter::Setup()  で 1 人ぶんの「実体」を作る
        ↓
 試合中はこの実体を毎フレーム進める
```

**設計図（`CharacterStats`）と実体（`Fighter`）を分けてある**のが要点です。
「最大体力 10000」は設計図、「今の体力 3200」は実体が持ちます。
ラウンドをやり直すときは、設計図から作り直すだけで済みます。

編集結果は必ず `%APPDATA%\Kakuge\` に保存され、`data/` の元データは
書き換えません。おかしくしてしまっても、保存先のファイルを消せば
元に戻ります。

## 5. 入力まわり（なぜ「押した瞬間」だけを見るのか）

`Fighter::NewlyPressedButtons()` は「今フレームで新しく押されたボタン」だけを
返します。押しっぱなしを含めると、ボタンを押している間じゅう技が出続けます。

しかし「押した瞬間」だけを見ると、今度は別の問題が起きます。
**動けないフレームに押したボタンが、そのまま消えてしまう**のです。
ヒットストップ中に次の技を押しても、動けるようになったときには
「押した瞬間」はもう過ぎています。これでは目押しでしかコンボがつながりません。

そこで **先行入力（インプットバッファ）** を持ちます。

```
押されたボタン → InputQueue に 6 フレームだけ保存
動けるようになったフレームで、まだ生きているものを技の候補に混ぜる
```

期限を数える時計（`BufferClock`）は、**止まっている間は進めません**。
進めてしまうと、止まっている 10 フレームの間に先行入力が期限切れになり、
「ちゃんと押したのに出ない」が起きます。

コマンド技（236 など）の判定は `CommandParser::Matches()` です。
数字が「その順番で現れるか」だけを見て、連続している必要はありません。
人間の入力は必ずブレるので、厳密な連続を要求すると誰も技を出せません。

## 6. 絵の描かれ方

キャラクターの絵には 2 通りあり、**自動的に切り替わります**。

```
data/sprites/<キャラクターID>/sprites.json がある？
   ├─ ある  → その画像で描く         … platform/Sprite.cpp
   └─ ない  → 図形を組み立てて描く   … platform/Figure.cpp
```

画像の差し替え方は [../data/sprites/README.md](../data/sprites/README.md) に
まとめてあります。大事な点だけ再掲すると:

- 絵は必ず**右向き**で描く（左向きは自動で反転）
- コマの中の「足の裏の位置」（`originX` / `originY`）がずれると絵が浮く
- **当たり判定は絵とは無関係**。絵を変えても強さは変わりません

描画は「今の状態を絵にするだけ」で、**状態を変えません**。
`Render()` の中でキャラクターを動かしてしまうと、
描画の回数（＝パソコンの速さ）でゲームの速さが変わってしまいます。

## 7. 直したいとき、どのファイルを見るか

| やりたいこと | 見るファイル |
|---|---|
| 技の強さ・フレームを変える | `data/moves/ryu/*.json`（またはゲーム内のエディタ） |
| キャラクターの速度・体力・体の大きさを変える | `data/characters/ryu.json` |
| 当たり判定のルールそのものを変える | `engine/Boxes.h`, `engine/BattleSystem.h` |
| 技の段階（発生・持続・硬直）の扱いを変える | `engine/MoveExecutor.h` |
| 移動・ジャンプ・ガード・状態の移り変わり | `engine/Fighter.h` |
| コマンド入力の受け付け方 | `engine/InputSystem.h` |
| CPU の強さ・考え方 | `engine/CPUAI.h` |
| 画面の見た目・文字・配色 | `platform/Screens.cpp`, `platform/Palette.h` |
| 体力ゲージ・判定の可視化（F1） | `platform/Hud.cpp` |
| キャラクターの絵（図形） | `platform/Figure.cpp` |
| キャラクターの絵（画像） | `platform/Sprite.cpp`, `data/sprites/` |
| キー割り当て | `platform/Game.cpp` の `BuildPlayerInput()` |
| コントローラ | `platform/Gamepad.cpp` |
| エディタの項目を増やす | `platform/Editor.cpp` の `BuildXxxFields()` |

## 8. 用語集

| 言葉 | 意味 |
|---|---|
| フレーム | 1/60 秒。格闘ゲームの時間の最小単位 |
| 発生 | ボタンを押してから攻撃判定が出るまで |
| 持続 | 攻撃判定が出ている長さ |
| 硬直 | 攻撃が終わってから動けるようになるまで |
| 硬直差 | 攻撃側と防御側の、どちらが何フレーム早く動けるか。＋なら攻撃側有利 |
| のけぞり | 攻撃を食らって動けない時間 |
| ガード硬直 | ガードして動けない時間 |
| ヒットストップ | 当たった瞬間、両者の時間が止まる演出。硬直差には影響しない |
| キャンセル | 技の途中で次の技に移ること。コンボの仕組み |
| 差し合い | お互いに技を当てに行く間合いの読み合い |
| 確定反撃 | ガードしたあと、相手が動けない間に必ず当たる反撃 |
| 中段 / 下段 | 中段は立ちガードでしか防げない。下段はしゃがみガードでしか防げない |
| ダウン | のけぞりではなく、倒れて起き上がるまで動けない状態 |
| 目押し | 先行入力に頼らず、動けるフレームちょうどにボタンを押すこと |
